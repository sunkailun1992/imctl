# B36：发送前输入框两轮视觉观察实施计划

> 规格见 `docs/superpowers/specs/2026-09-26-b36-send-composer-visual-observation.md`。本计划只覆盖 `message.send` 与 `message.sendFile` 的可逆暂存前后观察。真实发送需新的目标与条数授权；本批计划本身不执行发送。

## Global Constraints

- 不修改编译白名单、`ActionPolicy` / `SendPolicy`、`CommandExecutor` 不可逆点、幂等、速率、checkpoint 语义、`KeystrokeInjector` 按键清单或屏幕录制范围。模型不选择多个编辑框、不写 payload、不触发 `⌘V` / Return、不决定成功。
- 只给显式固定方法使用经核验的企微主窗口；云端总开关、整窗开关与系统授权三门缺一不可。截图与模型原文只在内存，所有测试用合成 AX / 假传输；源码、测试、报告不写凭据、签名地址、真实联系人 / 消息或截图。
- B34 的选会话前缀仍先执行；B28 的唯一聊天输入框与单附件守卫仍是写入准入。视觉失败发生在提交前时不换提供商、不重试粘贴或提交；提交后证据不足 `unknown`。

## Task 1：锁住动作前 AX 准入与测试边界

1. 在 Fake AX 测试中先构造目标已活动、唯一空 `AXTextArea`、完整消息基线；断言进入新视觉阶段前没有 AX 写 / 按键 / checkpoint。构造两个底部可写输入框、已有草稿、缺消息表、目标不符及策略拒绝，断言截图和请求为零。
2. 在 `WeComCommandHandler` 的显式方法入口挂方法专属的视觉准备闭包；`WeComActions.submit` / `sendFile` 仍拥有输入框解析、原文写入或粘贴与提交。闭包只能观察或否决既有动作，不能返回新的收件人、内容、文件 URL、按键、坐标或替代 AX 句柄。后台调用与 `message.broadcast` 不安装 B36 闭包。
3. 在视觉阶段冻结并重核 PID、主窗口句柄 / frame、活动目标、输入框句柄 / role / frame、策略、暂停、命令方法与本机视觉开关。无唯一 AX 输入框时保持 B28 的 `ambiguous composer` 失败，不能调用模型猜。

## Task 2：暂存前后两轮与原动作集成

1. 暂存前截一帧经核验窗口，给模型固定 `.control(.messageComposer)` 目标和唯一 AX 输入框的匿名候选框作为画面锚点，但允许步骤仅为 `verify/reobserve/stop`，不得让模型选 `writeText`；`verify` 只让本机再次检查输入框为空、目标和准入仍一致。复用观察器的候选句柄限制，不开放其它编辑框。模型 `stop` / 无效响应 / 超时不得写 AX、粘贴或落 checkpoint。
2. 检查通过后，文本沿 `setComposer(request.text)` 原路径仅写一次；附件沿原校验、outbox、剪贴板恢复和一次 `⌘V` 原路径。视觉接口不能修改 payload；动作前后重新核对同一输入框与目标。附件暂存保留 U+FFFC / 单原生对象检查，不使用模型图像判断文件身份。
3. 暂存后用当前企微窗口的**新截图**再请求同一模型，第二轮仅 `verify/reobserve/stop`。只有模型未否决且新的 AX 读回为相同目标、相同输入框、精确文本或严格单附件暂存，才沿原代码写 checkpoint，随后一次 Return / 既定 submit 策略，再用原外发气泡后验决定终态。把文本的 checkpoint 写入点保持在不可逆动作之前、两轮可逆观察之后；附件 checkpoint 也只在严格暂存后写。
4. 若第二轮或 AX 后验失败，文本仅在能证明是同一目标 / 输入框 / 原文时清理本次暂存值；人工更改一律保留。附件不重复粘贴，也不提交；企微暂存界面可能仍有 chip，但外层会清理临时 outbox 文件，不能保证人工可继续发送，需人工检查并清理。提交后任何模型或 AX 读取异常均按现有不确定性规则保留 `unknown`，不得变成可盲重试的 `failed`。

## Task 3：聚焦测试与守卫回归

1. Fake 模型测试顺序：首帧→模型 `verify`→唯一固定暂存→第二新帧→模型 `verify`→AX 后验→checkpoint→**一次**提交→新 outbound 证据。断言目标已活动时两次截图 / 两次请求；非活动目标时 B34 前缀加两次且六轮 / 40 秒总预算不被重置。视觉关闭沿 AX 路径零请求。
2. 逐一注入首轮 / 次轮 `stop`、429 / 超时、授权 / 提供商 / 策略 / 暂停变化、PID / 窗口 / frame / 输入框 / 会话漂移、AX 暂存读回失败、手工草稿变化、文件暂存出现额外字符 / 多对象；断言不会提交，保留他人草稿，且没有截图、内容或模型原文进入结果 / 事件 / 日志。模型 `verify` 不能单独产生成功。
3. 回归 B28 的双编辑框与草稿守卫、B33 的单原生附件与提交后 `unknown`、B34 选会话、同键回放、`ForbiddenAPITests`、协议文档守卫。代码完成后运行聚焦测试、`swift build`、全量 `swift test`、`git diff --check`、`bash scripts/check-secrets.sh`；若文档中的视觉范围或交互阶段变化，同一提交更新 README、协议 §4.1 / §6.5 / §6.6、运维与随包文档。

## Task 4：活体门报告与发布边界

1. 主执行者用稳定签名安装版核对 `setup --check`、视觉配置和 `controller.describe` 计数基线；先做不发送的只读命令验证客户端、MQTT 与模型配置。Fake 通过不等于真实企微或云端通过。
2. 没有新的发送授权时不通过 MQTT 触发 `message.send` / `.sendFile` 的真实提交。本批门报告写发送数 **0**、两种 B36 活体链**待验**，不能拿 B33 四条历史发送或 B34 只读视觉成功作本批发送证明。得到新的目标与条数授权后，仅向用户自己的文件传输助手执行精确获准的测试项；每项只提交一次，记录匿名视觉计数差分、AX 暂存后验、实际新外发证据、`command.get`、终态事件和唯一幂等键回放，不记录聊天正文或签名 URL。
3. 分开记录源码 / fake、真实 Qwen 或 Gemini、真实企微、MQTT、本机包与第二台 Mac。若模型请求成功但 AX 或消息后验失败，标明失败或 `unknown`；只有模型请求差分、AX 读回与 MQTT 终态三层同向时，才认定该方法本次多轮视觉分支活体通过。
