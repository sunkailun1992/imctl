# B32 发送结果的方向与新消息证据规格

## 问题与范围

`message.send` 在不可逆提交后的确认阶段，当前以“正文相同且行索引不在基线中”判成功。若同时收到相同正文的入站消息，或 AX 无法确认方向，结果仍可能被记为 `succeeded`。索引随历史加载变化，也不是稳定的消息身份。

`message.sendFile` 已用消息键、外发方向和可读文件名核对新附件。本批复核该路径的失败关闭边界，并使协议文字与实现一致；不增加自动重试、模型权限、按键、白名单或新的协议字段。

## 成功证据

- 文本：提交前取得完整的当前会话消息基线；提交后，只有**新出现的、正文与请求完全相同、方向为 `outbound`** 的消息行才是成功证据。消息键须不在基线中；已加载消息还须保持原顺序作为后验前缀，候选不得与基线中任一行在内容、发送者、时间及类型上不可区分。重复同文无法证明是新发时保持 `unknown`。单凭新行索引、输入框清空、模型判断或画面上“像是发送了”均不构成成功。
- 附件：后验须是基线中没有的外发消息，且**类型与请求匹配**：图片 `media`、视频 `video`、其它文件 `file`。文件卡片及任何暴露文件名的附件行须与本次粘贴的净化文件名一致；原生视频若客户端没有提供文件名，可用新消息键、外发方向和视频类型取证。无文件名的图片可用新键、外发方向和媒体类型取证；若与基线旧图不可区分，保持 `unknown`。
- 方向统一经 `WeComReader.chatMessages` 归一化。确认为当前账号自聊的**精确** `文件传输助手` 会话，其消息归为 `outbound`；其它会话的 `inbound` 或 `unknown` 不得算发送成功。不得把“目标看起来像自聊”推广到任意会话。
- 基线中任何消息的 AX 内容读取失败、使该行及后续键不可信时，提交前停止，不能丢掉 nil 键继续发送。提交后每轮取证前后均复核当前活动会话；若切走或标题读不回，立刻记录 `unknown`，不得拿另一会话的气泡取证。某轮 AX 消息读取失败、方向未知或缺键只跳过该轮等待；达到既有超时且附件或文本已离开输入框时保持 `unknown`，不把它改写为 `failed` 诱导重发。

## 状态与不可逆边界

- `ActionPolicy`、目标与输入框复核、提交前 checkpoint、`afterIrreversible` 崩溃钩子、限速和幂等保持既有顺序。`succeeded` 仅在上述客户端证据成立时写入 checkpoint，并沿既有 MQTT/MCP `command.state` 回传。
- 回车或按钮已执行后，只有入站、方向未知、键缺失或文件名不符的候选时不能报成功。输入框仍保留本次内容且 AX 读取完整，可沿既有失败清理规则；输入框已清空或后验 AX 不可靠为 `unknown`，同键回放原结果，绝不自动重试。
- B17 视觉模型可帮助固定命令定位控件，但不能自行确认发送成功、补造方向或改变目标和正文。发送后仍以解析到的客户端消息证据为准。

## 验收边界

Fake AX 至少覆盖：新外发同文成功；新入站同文、未知方向同文、旧行重新编号及旧同文前插均不成功；自聊归一化仍可成功；基线不完整在不可逆点前停下；提交后会话切换为 `unknown`。附件回归覆盖新外发的图片 / 文件 / 视频，以及入站、未知方向、错误类型、文件名不符、旧媒体前插和不完整基线。全量构建、测试、敏感扫描和 diff 检查后，真实发送必须由主智能体按已批准的测试目标和条数另做受控活体；未执行时门报告明确“待活体”。
