# B57：群名视觉检查前恢复可见主窗

B56 的公开 1.0.20/build 4 已按维护者批准安装；一次受限改名请求在 prepare/round 0 以 `staleView` 失败，checkpoint 为 0。按约定停止，没有新键重试、实际改名或恢复操作。群名步骤的截图 / 模型请求 / HTTP200 增量均为 0，因此不能据此判定 B56 提示是否有效。

随后只读 AX 检查发现 `AXWindows` 是明确的空数组，但 `AXMainWindow` 与 `AXFocusedWindow` 仍可达原标准主窗，原目标群和选中行可读；窗口服务读回该应用窗口均不在当前屏幕。`WeComWindowLocator` 已记录另一 Space 的此类行为；原 B55 要求一或二个窗口，空集合必然拒绝。不能把空集合直接当成“没有冲突窗口”，也不能忽略未知对话框。

只对外部 `group.rename`、既有 B37 观察已安装且明确空窗口数组的命令增加一次前置恢复：

1. 冻结原应用 / 主窗 / focused window 的 backend、PID、handle、有限 frame，以及唯一原选中行的 handle 和精确目标 title、活动标题。unsupported、nil、非数组或 AX 错误不是“空窗口”。
2. 在任何群名 focus / value、checkpoint 或模型请求之前，检查原策略、pause gate、视觉设置、录屏授权、方法 / origin 与命令预算；沿用已用于导航的 `AXFrontmost=true`，只请求一次，不加合成按键。
3. 有界等待明确的窗口数组重新列出原主窗。每轮重查授权、设置和原窗口 / 选中行 / title / frame；任何变动停止，不重选目标、不更换基准、不再次激活。
4. 恢复可见后才进入原改名路径；完整 B37 与 B55 窗口检查仍须通过，未知对话框、第三窗或零窗依旧拒绝。模型停止、字段检查、早生效核对、checkpoint、幂等、权限及抓图范围均不变。
5. 前景保持到整个改名动作（包括既有草稿还原 / unknown 处理）结束，随后以已有 helper 尝试恢复原前景；恢复不是成功证据。原本有窗口、非 B37 路径与 window-only legacy fake 不新增前景操作。

离线用 app-rooted fake 证明空集合恢复与守卫继续生效，覆盖超时、激活失败、原锚点变更、额外窗口、撤权及异常后的前景恢复。源码顺延到 1.0.21-dev。维护者已授权本人账号与 AI 协作 PR 经必要 CI 全绿后直接合并；第三方仍需本人审核。B57 没有新增真实改名或模型请求许可，本批不执行该类动作，不能以离线通过声称实机验收完成。
