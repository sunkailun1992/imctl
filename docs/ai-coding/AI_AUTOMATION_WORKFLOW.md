# AI 自动化开发流程

本文约束 AI 在 `imctl` 的任意批次中按统一流程完成需求理解、计划、实现、验证、门报告和分支 / PR。维护者可另行归档私人 wiki，但它不是外部贡献的依赖或验收条件。只保留通用流程，不写 broker 地址、凭据、真实联系人或本机绝对路径。

## 一、标准流程（一个批次）

1. **读上下文**：`AGENTS.md` → `docs/ai-coding/` → 当前规格（`docs/superpowers/specs/`）→ 上一批门报告与计划 → 当前 issue / PR 的用户决定。已批准的设计不重新讨论。维护者可补充私人 wiki 的脱敏交接依据，不能要求外部贡献者访问它。
2. **头脑风暴（仅当没有已批准规格）**：澄清需求并写规格到 `docs/superpowers/specs/`，等用户批准；有 superpowers `brainstorming` 时可辅助，没有插件时按本仓库模板完成。
3. **写计划**：写 `docs/superpowers/plans/YYYY-MM-DD-<批次>-<主题>.md`：目标、架构、Global Constraints（白名单、合成输入、权限面、脱敏、用户事项）、逐任务的失败测试 → 实现 → 通过 → 提交，接口签名前后一致，无占位符。有 superpowers `writing-plans` 时可辅助，不作为必装依赖。
4. **批量实现（TDD）**：每个任务先写测试代码再写实现；用户约定"批量实现后一次 `swift test`"，因此逐任务可只做编译检查，最终全量测试一次；任务内不绕过策略 / 执行器 / 守卫。
5. **一次 `swift test`**：普通贡献显式设置 `IMCTL_LIVE=0 IMCTL_LIVE_VISION=0`，全部通过并记录测试数；失败先复现并找根因，有 superpowers `systematic-debugging` 时可辅助，不为通过而放宽断言或守卫。
6. **活体 E2E**：按 `TESTING_SPEC.md` 的规则对真实客户端验证：只读探针 → 受限动作 → 受控发送（仅测试目标、先确认条数）；依赖用户事项未到位时只做只读并如实写"待活体"。
7. **门报告**：`docs/gates/YYYY-MM-DD-<批次>-<主题>.md`，写条件、实现、单测数字、活体表、结论与未闭环、需要用户决定的事项。
8. **提交与合并**：按 `AI_CODING_GUIDE.md` 第 11 节；开工、提交前、推送前先 `git fetch`。维护者本机会话验证全过后可直接合并到 `main`，合并后看 CI；云端会话只推 `claude/<主题>` 分支；其他人推工作分支或自己的 fork 并开 PR，由 @sunkailun1992 本人审核批准。不强推、不改写已推送历史；AI 不代替本人 approve。
9. **可选的私人 wiki 归档**：仅维护者有相应访问和授权时执行：证据进 `queries/`，口径覆写 topic / repo / synthesis 路线页，仓库事实覆写 `repos/imctl.md`，复核登记，`log.md` 追加，重建索引并校验，提交推送 wiki。公开 PR 的必要事实必须留在仓库或 PR 中，不因未访问私人 wiki 阻塞贡献。
10. **交接**：在 PR 或仓库文档列明未闭环与用户事项；维护者可另写私人 wiki `handoffs/`。

## 三、验收标准模板

```markdown
# AI 验收标准 - <批次 / 主题>

## 单测
- [ ] 新增类型 / 方法 / 字段各有失败先行的测试。
- [ ] 策略拒绝前无 AX set / action。
- [ ] 幂等 / 过期 / 暂停 / 速率 / 崩溃后 unknown 覆盖（涉及执行器时）。
- [ ] `tools/list` 数量、CLI 子命令列表、`ProtocolTests` 同步。
- [ ] `ForbiddenAPITests` 通过。

## 安全
- [ ] 白名单未改；策略只放宽；`unknown` 类型不放行。
- [ ] 无凭据 / broker 地址 / 联系人内容 / 本机路径进入仓库。
- [ ] 运行数据文件权限（0600 / 0700）有测试或说明。

## 活体
- [ ] 只读探针结果（脱敏）。
- [ ] 受限动作 / 发送：目标、条数、证据。
- [ ] 依赖用户事项的项如实标"待"。

## 文档
- [ ] README / 契约 / ops / AI 规范同步。
- [ ] 门报告写成并链接计划。
- [ ] 公开交接依据完整；维护者若另行归档私人 wiki，记录其校验结果（外部贡献不要求）。
```

## 五、多智能体流程

- 主智能体负责需求边界、模块归属、实现方案、PR 准备、测试结论、活体动作、提交说明与风险判断；合并遵守根目录 `MAINTAINERS.md`：维护者一侧可直接合并，其他人的改动须本人审核批准。
- 子智能体默认只做代码阅读、AX 树分析、门报告核对、测试缺口分析、Review、日志分析。
- 子智能体不得提交、推送、切分支、修改未分配文件、写入凭据 / broker 地址 / 联系人内容 / 本机路径，不得对真实客户端执行任何动作。
- 多个 worker 只有写入边界清楚时才并行（例如一个只改解析与其测试，一个只改 CLI）；策略、执行器、`KeystrokeInjector`、传输守卫、守护进程装配由主智能体串行处理。

## 六、子智能体输出要求

- 结论：模块归属、调用链、配置状态或异常原因。
- 证据：类型名、方法名、文件与行号、夹具节点路径、日志关键字。
- 风险：是否影响策略、不可逆点、事件语义、传输守卫、运行数据、部署脚本。
- 建议：只提建议，不替主智能体做最终决策。
