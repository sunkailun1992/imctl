# B54：独立「发送验证申请」窗口的邀请提示与视觉轮次记录

## 背景与目标

B51 让 `contact.add` 认出企业微信用户的独立「发送验证申请」窗口：
- 只认实录形状；
- 按下结果行「添加」前记快照，按后据此确定归属；
- 截图只截按后新出现、已证实窗口号的那个窗口。

这些在 build 233 活体通过。但授权的真实添加停在邀请轮：第二个 checkpoint 没写，「发送」没按，申请没发出。停止原因没留下任何记录，最可能的情况是：
- 邀请轮提示仍按「面板内邀请」写成：要求从截图看出邀请属于「本命令选中的结果」，又写「出现另一个对话框就停」；而独立窗口的截图里只有这个窗口，看不到结果列表。
- 越过第一个 checkpoint 后，执行器只记 `unknown` 和一句固定的话，原来的停止原因被丢掉。诊断只有三个累计计数（截图、请求、HTTP 200）。

本批要做到：
- 每一轮视觉的结果都有记录，命令因视觉停下或出错时，命令记录里能看到停在哪、为什么、越过了几个不可逆点；
- 独立窗口的邀请轮有一套与截图相符的提示，真实添加能走到 `requested`；
- 结果行提示写明本命令选中的来源。

## 用户决定（2026-10-13）

- 范围：B51 交接的三项（每轮视觉结果记录、独立窗口单写邀请提示、用户点头后真实添加一次），加上「结果行提示写明所选来源」。
- 视觉结果同时记在守护进程日志和命令记录里。
- 邀请轮采用「独立窗口单独一套目标与提示」：保留写入前的画面复核；面板内邀请的旧提示不动。
- 原定 B53 的这项顺延为 B54；版本号改为 1.0.17-dev。
- 实施中补充（2026-10-13 14:26 / 14:55）：`contact.add` 不再要求号码白名单，任何号码都可搜索与发申请（对方通不通过由对方决定）；每小时上限保留。旧策略文件里的号码列表读入后忽略，`policy.set` 的 `allowPhones` / `denyPhones` 不再生效；控制台去掉「放行此号码」，体检改为显示「号码不限」和上限。
- 再补充（2026-10-13 15:3x，审查后用户决定）：只搜索（dryRun）另设每小时上限，默认 60；控制台「发送添加申请」先弹确认（显示打码号码与来源）；智能体技能写明先只搜索、只加用户当次指定的号码。另外只收手机号形式（5–20 位数字），`policy.json` 无法解析时两个上限都按 0。

## 视觉轮次记录

**守护进程日志**：每次请求模型后写一行，只含固定类别：

```
vision round <method> <目标>/<阶段> #<轮次> → <结果> (<毫秒> ms)
```

- `<目标>`：`AIPlannerControlPurpose` 或行目标、滚动目标的固定名字。
- `<阶段>`：`AIPlannerPhase`，如 prepare / verify / commit。
- `<结果>`取以下之一：
  - 模型所选步骤：verify、reobserve、stop、press、writeText 等，不带候选编号或文字；
  - 或现有 `AIPlannerVisionError` 的固定名字：timeout、invalidHTTPStatus、invalidResponse、invalidChoice、staleView 等。
- 不记截图、模型原文、候选标签、目标会话、号码、验证语、提示词。
- 所有显式视觉命令共用，在轮次执行器的统一出口实现一次。截图、请求、HTTP 200 三个累计计数照旧。

**命令记录**：命令因视觉停下（模型选 stop）或视觉出错而结束时，在记录上留一个可选的 `diagnosis` 对象，只含固定类别：

```json
{"visual": {"goal": "contactSendVerification", "phase": "commit", "round": 1, "outcome": "stop"}, "irreversibleSteps": 1}
```

- `irreversibleSteps`：本命令越过的不可逆点数。`contact.add` 的第 1 个是按结果行「添加」，第 2 个是按「发送」；`message.send` 等只有 1 个，是提交。
- 越过 checkpoint 后仍记 `unknown`、错误码仍为 `UNKNOWN_AFTER_CHECKPOINT`，含义不变；`diagnosis` 不再被丢掉。没越过时照旧记 `failed`，同样带 `diagnosis`。
- `command.get`、`command.state` 事件与 MQTT 回复都带它；没有 `diagnosis` 的记录与旧版一致。
- 存储：命令表加一个可空列。
- 协议文档（命令记录一节与 `contact.add`）写明字段、取值和 `irreversibleSteps` 的含义。

## 独立窗口的邀请轮

- 新增视觉目标 `contactSendVerification`（本命令自己的「发送验证申请」窗口里的「发送」按钮）。只有当候选按钮在本命令证实的独立邀请窗口里时，处理器才用它。
- 面板内邀请、主窗弹层邀请继续用 `contactInvite` 和原提示，一字不改。
- 新提示的必要内容（英文写成，与其它提示一致）：
  - 调用方已用 AX 证明：
    - 这个窗口是按下本命令所选结果的「添加」后新出现的，窗口号已证实；
    - 窗口里恰有一个单行输入框（其中验证语已核对）、一个「发送」、一个关闭按钮。
  - 截图里只有这个窗口，看不到搜索结果，也不需要看到。
  - 框住的「发送」只是图上的位置标记：模型不能按，不能改字，不能宣称申请已发出。
  - 模型的选择：
    - verify：截图是这样一个窗口，框住的正是其中的「发送」；
    - reobserve：窗口还在加载；
    - stop：截图是别的窗口（聊天窗、提示框等），窗口里出现报错或限制提示（例如已是客户、操作过于频繁、查无此人），或框住的不是「发送」。
  - 不写「出现另一个对话框就停」。
- 模型权限不变：这一轮只能 verify / reobserve / stop。「发送」仍由代码在第二个 checkpoint 之后按；按后以窗口从窗口列表消失为 `requested` 的证据，仍开着为 `confirm-pressed`（执行器记 `unknown`）。

## 结果行提示写明来源

- `contactMatch` 的复核提示写明本命令选中的来源：微信或企业微信。同号的两行里，模型据此知道看哪一行。
- 只改提示文字；唯一的来源结果行仍由 AX 证明，模型仍只能 verify / reobserve / stop。

## 安全与隐私

- 每小时上限照旧（号码白名单按上面的补充决定去掉）；dryRun 不越过第一个不可逆点。
- `unknown` 只按原幂等键对账，不换键自动重试；真实添加每次都要用户当次授权。
- 日志与 `diagnosis` 只有固定类别；号码照旧掩码；截图、联系人、验证语、模型原文不落地。
- 不新增系统权限与网络端点；`ForbiddenAPITests` 不放宽；整窗截图与上传条件不变。

## 测试与验收

- **单测**：
  - 每种轮次结果（各步骤、各错误类别）都恰好写一行日志；上下文里放进号码、会话标题、验证语时，日志行与 `diagnosis` 都不含它们。
  - 越过 checkpoint 的 `unknown` 保留 `diagnosis`；未越过的 `failed` 带 `diagnosis`；非视觉原因结束的命令不带。`irreversibleSteps` 对 `contact.add` 的两个点分别为 1、2。
  - 记录编码与解码：带与不带 `diagnosis` 都能读写；旧记录读出没有它。
  - 邀请在独立窗口时选 `contactSendVerification`，在面板内或主窗弹层时选 `contactInvite`。
  - 新提示不含「另一个对话框就停」的意思，写明截图里只有该窗口；`contactInvite` 的提示与本批之前一字不差。
  - 结果行提示含所选来源。
- **变异**：逐条删掉以下保证，都应有测试变红：
  - 日志去敏；
  - `unknown` 保留 `diagnosis`；
  - `irreversibleSteps` 计数；
  - 独立窗口才用新目标；
  - 旧提示不变；
  - 新提示不含「另一个对话框」；
  - 结果行写明来源。
- **审查**：最终整分支审查由新的审查代理完成，严重与重要问题在一轮修复里改完。
- **活体（这台 Mac，企业微信 5.0.12）**：
  1. 用户准备自有测试号：须是企业微信用户，且当前不是客户。号码由用户自己在控制台填，不进对话、代码和 Wiki。
  2. 来源选企业微信做 dryRun：在日志里核对每一轮的记录和结果行提示的来源。
  3. 用户点头后，用新键真实添加一次。期望：
     - `requested`，验证窗口从列表消失，对方收到申请；
     - 如果停下，`diagnosis` 写明停在哪一步、越过了几个不可逆点。
  4. 如果 5.0.12 的窗口形状与 5.0.11 不同而识别失败，命令在按「添加」之前停止；记下差异，是否补校准由用户决定。
- 门报告写 `docs/gates/<日期>-b54-verification-invite.md`；合入 main 与推送前问用户。
