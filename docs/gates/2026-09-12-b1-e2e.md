## E2E 2：崩溃注入（`IMCTL_CRASH_AFTER=submit`）

1. `message.send`（文本 `imctl-b1-crash`，幂等键 `crash-…`）：回车投递后、取证前进程 `exit(70)`；无响应；DB 中该命令 `running` + `checkpointMs`。
2. 重启 `imctld`（同一 DB）：日志 `recovered command … -> unknown (checkpoint without evidence)`；`command.get` → `state=unknown, error.code=UNKNOWN_AFTER_RESTART`。
3. 同一幂等键再次 `message.send` → 返回同一 `unknown` 记录，**不重跑**。
4. 客户端消息表里 `imctl-b1-crash` 恰好 1 条。

## 安全审查修复与 socket 活体验证（01:3x CST）

后台提交审查指出 `UnixSocketServer` 先 `bind` 再 `chmod`，中间存在本地任意进程可连接的窗口——而这个端点能执行 `message.send`。已改：

- 改用 POSIX socket 自行 `bind`（Network.framework 在该路径下根本没创建 socket 文件，这也是之前 socket 从未真正可用的原因）；`umask(0o177)` 覆盖整个 bind 窗口并加进程内锁，父目录必须已是 0700，绑定后再校验 socket 自身 mode，任一不满足即 `close`+`unlink` 并抛错，不再吞掉错误。
- 拒绝超过 `sun_path` 上限（103 字节）的路径，错误明确。
- 实测：`srw------- s.sock`、`drwx------` 目录；经 socket 调 `account.status` 与 `message.send` 成功，同幂等键回放返回同一 commandId 不重发。

同时修掉一个真实缺陷：`imctld` 里 socket server 是局部变量，出作用域即释放，内核接受连接但无人 `accept`（外部看起来就是"连上了但永远没响应"）。现由 `DaemonRuntime` 持有传输与 watcher，并处理 SIGTERM/SIGINT/SIGHUP：实测 `kill -TERM` 后日志打印 `received signal 15`，socket 文件与状态文件都被清理。
