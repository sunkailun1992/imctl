# B29：群名确认前的有界读回

## 问题与范围

`group.rename` 的头部 `AXTextField` 写值可能只回显或未保持，而 `AXConfirm` 可能已经让客户端提交改名。群名是否真的生效仍以**会话列表选中行**的新标题为准；确认后看不到该标题不能再按第二次确认。本批只改现有群名字段的确认前准备，不扩大 MQTT 方法、目标、策略、按键或模型可执行动作。`group.create` 复用同一写值 helper，保留自身已存在的整条创建流程和 checkpoint。

## 允许的步骤

1. 原命令先解析目标并做策略检查；字段解析唯一时仍走 AX 快路径，字段有多个 AX 候选时沿用已有的单次视觉候选选择。
2. 首次写入前检查原始标题、字段 PID / 角色 / 可写性 / 位置 / 句柄；对 `group.rename` 还要求**恰好一条选中会话行**仍为原群。每次写前与读回时都复核命令 gate 和同一字段。
3. 写入调用方给定的新群名后读回。若同一字段仍是原值且选中行仍是原群，可以再聚焦并**重写同一值一次**。若是其它值、目标变化、字段变化，或第二次仍未读到请求值，在 checkpoint 与 `AXConfirm` 之前停止。最多两次 AXValue 写入，不上传截图、不让模型生成名字或选第二个字段。
4. 读回成功才建立不可逆 checkpoint；checkpoint 后再次复核 gate / 字段 / 选中行，然后最多一次 `AXConfirm`。确认后只有**唯一仍被选中的会话行**改成请求名才是 `group.rename` 的后验；列表中其它同名行、无选中行或多选中行都不能证明这次改名。后验未出现时按既有流程仅做一次可逆 blur 与等待，结果保持 `unknown`，不重复确认。`group.create` 的新群行尚未稳定选中时保留原有精确标题回退。

## 证据边界

Fake AX 能证明值丢失、目标漂移与确认次数的控制；真实企微改名、云端视觉候选与 MQTT 终态需单独活体验收。没有测试群改名授权时，本批真实改名数为 **0**。协议与事件字段不变。
